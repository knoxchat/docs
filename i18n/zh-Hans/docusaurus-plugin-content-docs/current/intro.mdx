# 快速入门

**Knox** 是一个一站式、兼容 OpenAI API 和 Anthropic Messages API 格式的平台，通过单一端点即可访问数百个模型，并提供智能路由、自动故障转移和透明定价。它还搭配了 **Knox‑MS**——一个面向长时间运行的 Agent 和需要持久上下文的应用的记忆管理系统。

如果要使用 **KnoxCoder** 桌面编辑器，请打开 <Link to="/knoxcoder">KnoxCoder 指南</Link>（导航栏里博客旁边的标签）。本页是 HTTP API 文档。

### 核心功能

- **智能模型路由**：提供性能优先/成本优先/均衡等策略，支持自动故障转移和供应商指标监控。
- **多模态输入输出**：支持文本、图片、PDF、视频和音频输入，以及图像生成、视频生成、[音乐生成](/music)、[文本转语音](/text-to-speech)、[语音转文本](/speech-to-text)、[音色](/voices)、[语音转换](/voice-changer)、[人声分离](/voice-isolator)、[音效生成](/sound-effects)、[配音](/dubbing)、[强制对齐](/forced-alignment)，以及语音到语音的 [实时语音](/realtime)。
- **工具调用与 MCP**：兼容 OpenAI 工具调用规范，并可桥接 MCP 服务器。
- **联网搜索**：使用 `:online` 模型变体或 `web` 插件获取实时引用。
- **Jev（System One）**：对共享 state 提出 typed questions，返回结构化 answers（不是 LLM）。详见 [Jev](/jev)。
- **结构化输出与推理**：支持 JSON Schema 强制约束和标准化推理 token。
- **效率功能**：支持提示缓存和中间消息裁剪，优化长上下文处理。
- **可靠性保障**：零输出补偿保险，确保失败或空响应不会产生费用。

### Knox‑MS 记忆系统

Knox‑MS 遵循一条原则：**有界上下文，无界记忆**。每次调用都适配模型的窗口，而长期记忆没有上限，通过 BM25、ripgrep、知识图谱（个性化 PageRank）和摘要树按需检索。只有最可能有帮助的记忆会在令牌预算内被注入。您可以查看每条记忆为何被选中，也可以遗忘其中任何一条。它还支持自主规划、任务编排、自我修复和实时进度事件。了解更多请参阅 <Link to="/knox-ms-complete-doc">Knox‑MS 开发者文档</Link>。

const openai = new OpenAI({
  baseURL: 'https://api.knox.chat/v1',

## 设计理念

Knox 帮助团队在多个供应商之间构建可靠、高性价比的 SI 系统。我们相信未来是多模态、多供应商、以记忆为核心的。

### 为什么选择 Knox？

**价格与性能**。Knox 会在各供应商之间寻找最优价格、最低延迟和最高吞吐量，并让您自行决定优先级。

**标准化 API**。在切换模型或供应商时无需修改代码。开箱即用地支持 OpenAI 兼容的 SDK、工具调用和结构化输出。

**记忆优先的应用**。Knox‑MS 为长时间运行的 Agent 提供持久记忆、知识提取和自主规划能力。

**默认多模态**。图片、PDF、音频输入以及图像生成、视频生成和语音到语音 Realtime，让多模态工作流变得简单直接。

**统一计费**。无论您使用多少个供应商，都可享受简洁透明的计费方式，并附带零输出补偿保险。

**更高可用性**。自动故障转移和智能路由确保即使供应商宕机，请求也能正常处理。

### 模型 API 标准

我们的 Models API 在确认信息后，会第一时间免费公开所有 LLM 的关键信息。

### API 响应结构

Models API 返回标准化的 JSON 响应格式，为每个可用模型提供全面的元数据。该结构在边缘节点缓存，专为生产环境应用的可靠集成而设计。

### 根响应对象

```json showLineNumbers
{
  "data": [
    /* Array of Model objects */
  ]
}
```

### 模型对象结构

`data` 数组中的每个模型都包含以下标准化字段：

| 字段                  | 类型                                          | 描述                                                                            |
| ---------------------- | --------------------------------------------- | -------------------------------------------------------------------------------------- |
| `id`                   | `string`                                      | API 请求中使用的唯一模型标识符（例如 `"google/gemini-2.5-pro"`）       |
| `object`               | `string`                                      | 对象类型标识（始终为 `"model"`）                                             |
| `created`              | `number`                                      | 模型创建时间的 Unix 时间戳                                          |
| `owned_by`             | `string`                                      | 拥有该模型的组织                                                       |
| `permission`           | `ModelPermission[]`                           | 定义访问控制的权限对象数组                                   |
| `root`                 | `string`                                      | 根模型标识符                                                                  |
| `parent`               | `string \| null`                              | 若为微调版本，则为父模型标识符                               |
| `context_length`       | `number`                                      | 最大上下文窗口大小（令牌数）                                                 |
| `architecture`         | `Architecture`                                | 描述模型技术能力的对象                                   |
| `pricing`              | `Pricing`                                     | 使用该模型的价格结构                                                  |
| `top_provider`         | `TopProvider`                                 | 主要供应商的配置详情                                        |
| `supported_parameters` | `string[]`                                    | 该模型支持的 API 参数数组                                      |
#### Architecture 对象

```typescript showLineNumbers
{
  "modality": string, // 输入/输出流的概要描述（例如 "text+image->text"）
  "input_modalities": string[], // 支持的输入类型： ["file", "image", "text", "audio"]
  "output_modalities": string[], // 支持的输出类型： ["text"]
  "tokenizer": string // 使用的分词方式（例如 "Gemini"）
}
```

#### Pricing 对象

所有价格均以美元计，按每令牌/请求/单位计费。值为 `"0"` 表示该功能免费。

```typescript showLineNumbers
{
  "prompt": string, // 每个输入令牌的费用
  "completion": string, // 每个输出令牌的费用
  "request": string, // 每次 API 请求的固定费用
  "image": string, // 每个图像输入的费用
  "audio": string, // 每个音频输入的费用
  "web_search": string, // 每次网络搜索的费用
  "internal_reasoning": string, // 内部推理令牌的费用
  "input_cache_read": string, // 每个缓存输入令牌读取的费用
  "input_cache_write": string // 每个缓存输入令牌写入的费用
}
```

#### Top Provider 对象

```typescript showLineNumbers
{
  "context_length": number, // 供应商特定的上下文限制
  "max_completion_tokens": number // 响应中的最大令牌数
}
```

#### 支持的参数

`supported_parameters` 数组表示每个模型支持哪些与 OpenAI 兼容的参数：

* `include_reasoning` - 在响应中包含推理内容
* `max_tokens` - 限制响应长度
* `reasoning` - 内部推理模式
* `response_format` - 输出格式规范
* `seed` - 确定性输出
* `stop` - 自定义停止序列
* `structured_outputs` - JSON Schema 强制校验
* `temperature` - 随机性控制
* `tool_choice` - 工具选择控制
* `tools` - 函数调用能力
* `top_p` - 核采样

:::note 令牌计数差异
不同模型使用不同的分词方式（见模型结构中的 `tokenizer` 字段）。有些模型将文本拆分为多字符块（GPT、Claude、Llama 等），而另一些则采用不同方式（如 Gemini）。这意味着即使输入和输出相同，不同模型的令牌数（以及费用）也会不同。费用按所用模型的分词器显示和计费。您可以通过 API 响应中的 `usage` 字段获取输入和输出的实际令牌数。
:::

<div className="bg-white dark:bg-transparent rounded-md border border-slate-200 dark:border-slate-700 shadow-sm my-4">
  <Accordion type="single" collapsible className="w-full">
    <AccordionItem value="item-1">
      <AccordionTrigger>使用 API 时会记录哪些数据？</AccordionTrigger>
      <AccordionContent>
        我们会记录基本的请求元数据（时间戳、所用模型、令牌数）。我们不会记录提示或生成的输出，即使发生错误也不会。如果启用 Knox‑MS，记忆产物（记忆、摘要、搜索索引、知识图谱条目）会存储在您的账户中以提供持久性。您可以随时查看并擦除它们。
      </AccordionContent>
    </AccordionItem>
    <AccordionItem value="item-2">
      <AccordionTrigger>会与第三方共享哪些数据？</AccordionTrigger>
      <AccordionContent>
        Knox 是一个代理系统，会将您的请求发送给模型供应商以完成处理。我们与所有供应商合作，尽可能确保提示和生成的输出不被记录或用于训练。
      </AccordionContent>
    </AccordionItem>
    <AccordionItem value="item-3">
      <AccordionTrigger>使用聊天页面时会记录哪些数据？</AccordionTrigger>
      <AccordionContent>
        聊天页面与 API 适用相同的数据隐私规则。聊天页面中的所有对话都存储在您的设备本地，不会跨设备同步。可以在聊天页面导出对话。
      </AccordionContent>
    </AccordionItem>
    <AccordionItem value="item-4">
      <AccordionTrigger>如何删除 Knox‑MS 记住的内容？</AccordionTrigger>
      <AccordionContent>
        删除单条记忆使用 `DELETE /api/knox-ms/memory/{id}`；按 id 集合、会话、项目或全部（`all: true` 且 `confirm: true`）遗忘使用 `POST /api/knox-ms/memory/forget`；也可以删除会话。遗忘是传播式擦除：文本、其搜索索引条目、依赖它的摘要节点和知识图谱边，以及缓存或冷存储副本会一并移除。系统保留一条墓碑（id、原因和时间，不含内容），防止过期副本使该记忆复活，此后任何检索通道都不会返回已擦除的内容。详见 [Knox‑MS 文档](/knox-ms-complete-doc#forgetting--memory-api)。
      </AccordionContent>
    </AccordionItem>
    <AccordionItem value="item-5">
      <AccordionTrigger>我能看到 Knox‑MS 为何使用某条记忆吗？</AccordionTrigger>
      <AccordionContent>
        可以。每个 Knox‑MS 响应都包含 `knox_ms_meta.injected_memories`（放入提示的 `[mem:id]` 条目及各检索通道给出的排名）和 `call_id`。`GET /api/knox-ms/calls/{call_id}/explain` 显示选择背后的分数，`GET /api/knox-ms/calls/{call_id}/budget` 显示窗口如何分配。
      </AccordionContent>
    </AccordionItem>
  </Accordion>
